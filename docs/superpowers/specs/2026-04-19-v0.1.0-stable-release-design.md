# v0.1.0 稳定版发布过渡设计

## 背景

当前项目已经具备一套可工作的 beta 发布链路：

- Rust crate 版本已为 `0.1.0`
- npm 包 `ports-rs` 当前版本仍为 `0.1.0-beta.5`
- 推送 `v*` tag 时，`.github/workflows/release.yml` 会自动构建多平台 release 资产并发布 npm
- npm 发布会根据版本元数据自动选择 dist-tag，beta 对应 `next`，stable 对应 `latest`

这意味着项目距离稳定发行版并不缺少基础发布能力，主要缺口在于：

- 版本与用户安装入口仍停留在 beta 语义
- README 与发布文档的默认心智仍以 beta 为主
- 缺少日常 CI 守门，很多发布前检查只在 tag 发布时执行

本次设计的目标不是扩大功能范围，也不是冻结所有 CLI 输出细节，而是让项目从“可发布 beta”平滑过渡到“可稳定发布 v0.1.0 并默认向用户推荐安装”。

## 目标

本设计要达成以下目标：

- 结束 `0.1.0-beta.x` 发布节奏，发布 `v0.1.0`
- 将 npm 默认分发渠道切换为 `latest`
- 保持现有 GitHub Release 自动化发布链路可用
- 为日常开发补齐最小必要的 CI 守门
- 用稳定版文档替代 beta 版文档的主叙事

## 非目标

本设计不覆盖以下内容：

- 新增 CLI 功能或重构现有命令实现
- 扩大支持平台范围，如 Linux arm64 或 Windows arm64
- 引入签名、公证、checksum 发布自动化
- 将所有命令输出字段承诺为长期冻结接口
- 建立大规模跨平台端到端自动化测试体系

## 发布稳定性的定义

本次 `v0.1.0` 的“稳定”定义聚焦发布治理而非功能冻结，具体指：

- 用户可以通过 npm `latest` 或 GitHub Release 获得正确安装产物
- 发布资产命名、内容与安装脚本映射保持一致
- 发布前核心验证能在日常 CI 和 release workflow 中重复执行
- 核心命令在发布后的 smoke test 中能正常启动和运行

本次稳定性承诺不包括“0.1.x 内所有展示字段绝不变化”。如后续发现展示层细节需要调整，只要不破坏主要安装路径和核心命令使用方式，仍属于可接受范围。

## 现状评估

基于当前仓库状态，可以得出以下判断：

- `Cargo.toml` 已是 `0.1.0`，说明 Rust 包层面对稳定版版本号没有阻碍
- `package.json` 仍是 `0.1.0-beta.5`，说明 npm 仍是阻止稳定版切换的主要版本源
- `README.md` 默认安装命令仍是 `npm i -g ports-rs@next`，与稳定版目标不一致
- 现有 `release.yml` 已经具备 stable 发布能力，不需要重做发布主链路
- 仓库中已有较多 Rust 单元测试，但尚未看到独立的常规 CI workflow
- 发布说明文档仍以 beta runbook 为主，稳定版操作路径尚未成为默认文档

结论是：项目已经具备发布 `v0.1.0` 的基础设施，稳定版过渡的重点应放在版本对齐、文档收口、最小 CI 守门，而不是继续堆叠新发布机制。

## 方案选择

本次评估过 3 类路线：

### 方案 A：最小稳定发布

- 仅将 npm 版本切到 `0.1.0`
- 调整 README 为 stable 安装方式
- 按现有流程发布 `v0.1.0`

优点：改动最小，最快可落地。

缺点：仍然缺少日常 CI 守门，很多问题只能等到打 tag 时暴露。

### 方案 B：稳定发布 + 最低限度守门

- 包含方案 A 的全部内容
- 新增常规 CI workflow，在 PR 或 `main` 上执行最小回归检查

优点：在不扩大功能范围的前提下，明显提升稳定版可信度。

缺点：比直接发版多一层准备，但改动仍较小。

### 方案 C：稳定发布 + 强化跨平台自动验证

- 包含方案 B 的全部内容
- 继续补充更重的跨平台 smoke 测试或行为一致性验证

优点：长期收益更高。

缺点：投入明显增大，容易拖慢 `v0.1.0` 发布时点。

## 推荐方案

采用方案 B：稳定发布 + 最低限度守门。

选择理由：

- 当前发布主链路已经可用，不值得在 `v0.1.0` 前重新设计
- 现阶段最明显短板不是功能，而是缺少把回归问题挡在 tag 之前的机制
- 补一个轻量 CI workflow 的收益远大于成本，且不会引入额外产品范围

## 设计概览

稳定版过渡后的职责分层如下：

- Rust CLI：继续作为唯一功能实现来源，`cargo test` 作为核心正确性检查
- npm 包：继续作为面向用户的安装入口，安装时下载对应 GitHub Release 资产
- Release workflow：继续承担 tag 驱动的正式发布职责
- Regular CI workflow：新增，负责在日常开发阶段提前验证关键发布前提
- 发布文档：改为以 stable 为默认叙事，beta 文档退居历史参考位置

该设计只调整发布治理层，不主动修改命令行为与功能边界。

## 版本与发布策略

### 版本对齐

稳定版发布前，版本约束应为：

- Git tag：`v0.1.0`
- npm `package.json`：`0.1.0`
- Rust crate `Cargo.toml`：保持 `0.1.0`

如果后续进入 `0.1.x` 维护，三个版本源仍需保持相同版本语义，不再引入 beta 编号作为默认节奏。

### npm dist-tag 策略

稳定版发布后：

- `latest` 指向 `0.1.0`
- `next` 不再作为默认安装入口

未来只有在需要重新引入预发布测试通道时，才重新使用 `next`。默认策略应以 stable 用户路径为中心。

## 工作流设计

### 1. 常规 CI workflow

新增一个独立于 release workflow 的常规 CI 文件，用于 PR 和 `main` 分支的最小回归验证。

建议触发条件：

- `pull_request`
- `push` 到 `main`

建议执行内容：

- `cargo test`
- `npm pack`
- `PORTS_RS_SKIP_DOWNLOAD=1 node scripts/postinstall.js`

设计意图：

- 确保 Rust 逻辑回归不会等到 release tag 时才发现
- 确保 npm 包仍可正常打包
- 确保安装脚本的跳过下载路径仍可工作

这一层只做最小必要验证，不承担多平台正式构建职责，避免和 release workflow 重叠。

### 2. Release workflow

现有 `.github/workflows/release.yml` 保持为正式发布入口，继续执行：

- 校验 release 元数据
- 运行 Rust tests
- 生成 npm tarball
- 验证 `postinstall` skip path
- 构建四个平台 release 资产
- 发布 GitHub Release
- 发布 npm 包

稳定版所需的调整重点不在 workflow 结构，而在于确保：

- `v0.1.0` 与 `package.json` 版本严格一致
- stable 版本被解析为 `latest`
- release 资产命名与安装脚本平台映射保持一致

### 3. Smoke check

正式发布后，保留人工 smoke check 作为稳定版最后一道确认。

最低要求：

- 校验 GitHub Release 中四个平台资产齐全
- 校验 `npm view ports-rs version dist-tags` 中 `latest` 指向 `0.1.0`
- 本机执行：
  - `npm i -g ports-rs`
  - `ports --help`
  - `whoisonport --help`
  - `ports`
  - `ports ps`

如本机具备可验证端口，还可以补充：

- `ports 3000`
- `whoisonport 3000`

## 文档策略

文档需要从 beta 主叙事切换到 stable 主叙事。

建议调整方向如下：

- `README.md` 默认安装命令改为 `npm i -g ports-rs`
- 如仍保留 `@next` 说明，应退为补充信息，而非主入口
- `docs/release-checklist.md` 以稳定版发布为默认示例
- `docs/first-beta-release-runbook.md` 保留为历史 runbook，但不再作为默认发布操作文档

这样可以让用户、维护者和未来贡献者都围绕 stable 路径建立统一认知。

## 错误处理策略

稳定版过渡后的失败处理原则如下：

- 常规 CI 任一检查失败，不应继续推进到可发布状态
- Release workflow 任一关键步骤失败，不应发布部分缺失的正式资产
- 如果 npm 发布失败，不尝试覆盖同版本重发，而是修复问题后发布新的版本号
- 如果发布后 smoke check 发现稳定版入口异常，应优先修复安装/分发问题，而不是先扩展功能

该策略延续当前仓库对“明确失败优于部分成功”的倾向，适合 `v0.1.0` 阶段。

## 验收标准

`v0.1.0` 发布过渡完成的判定标准如下：

### 版本与分发

- `package.json` 版本为 `0.1.0`
- Git tag 为 `v0.1.0`
- npm `latest` 指向 `0.1.0`

### 发布资产

- GitHub Release 包含四个平台正式资产
- 资产命名与 `postinstall` 平台映射一致
- Unix 包包含 `ports` 与 `whoisonport`
- Windows 包包含 `ports.exe` 与 `whoisonport.exe`

### 自动验证

- 常规 CI workflow 可以在 PR 或 `main` 上自动通过
- `release.yml` 可在 `v0.1.0` tag 上完整跑通

### 用户路径

- `npm i -g ports-rs` 可完成安装
- `ports --help` 与 `whoisonport --help` 能正常启动
- 至少一次 `ports` / `ports ps` smoke test 成功

## 实施顺序

建议按以下顺序执行：

1. 新增常规 CI workflow
2. 将 `package.json` 版本改为 `0.1.0`
3. 将 README 与 release 文档改为 stable 默认叙事
4. 执行 preflight 验证
5. 创建并推送 `v0.1.0`
6. 完成 release 后的 smoke check

这种顺序可以先补齐守门，再做 stable 收口，最后完成正式发布，风险最低。

## 结论

`port-whisperer-rust` 当前已经具备从 beta 过渡到稳定版的基础条件。对 `v0.1.0` 最合理的推进方式不是继续扩功能，也不是重写发布系统，而是：

- 对齐版本
- 把文档默认入口切到 stable
- 增加最小常规 CI 守门
- 沿用现有 tag 驱动 release workflow 发布到 `latest`

这样可以以较小改动把当前“可用的 beta 发布链路”升级为“可信的稳定版发布链路”，并为后续 `0.1.x` 维护建立更清晰的工程边界。
